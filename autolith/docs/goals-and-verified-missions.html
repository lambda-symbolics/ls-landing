Goals and verified missions

Use a goal for work that can continue between messages. Use a mission if you want to define acceptance criteria, checks, and a budget before work begins.

  • Set a goal with (goal "OBJECTIVE"). A string such as "pause" is an objective, not an action.
  • Inspect it with (goal) or (goal :status). Change the objective with (goal :update "NEW-OBJECTIVE").
  • Pause, resume, or clear it with (goal :pause), (goal :resume), or (goal :clear). An unknown action signals application-goal-error without changing the goal.

By default, a lightweight goal pauses after eight automatic continuation turns between user messages. Change the saved limit with (settings :goal-continuation-limit 16) or remove it with (settings :goal-continuation-limit :unlimited).

Queued commands and Lisp forms run between goal turns. The goal only continues if it yielded to the queued input. If you interrupt goal work, send a message to continue. A job can still wake the session after a goal finishes without restarting that goal.

To set up and run a mission:

  1. Install the objective, limits, and acceptance criteria with (mission :start specification). This example requires both a passing build and your review:

    Common Lisp 
    (mission :start
 '(:objective "Deliver the accepted build"
   :turn-limit 40 :token-limit 100000 :wall-seconds 3600
   :criteria ((:id "build" :description "The build passes" :gates ("build"))
              (:id "review" :description "The user accepts the result"))
   :gates ((:id "build" :kind :command :command "make check"
            :inputs ("Makefile" "src/main.lisp") :deterministic-p t
            :attempt-limit 3 :timeout-seconds 300))))

  2. Run (mission :run) and inspect the saved state with (mission :status).

  3. Give explicit evidence for each criterion without a gate. If the mission is blocked on your review, accept the result and resume:

    Common Lisp 
    (mission :accept "review" "I inspected the artifact and accept the result")
(mission :resume)

  4. Request verification with (mission :verify). The model can also request it with its completion marker. A mission is verified only if every gate passes and every criterion is satisfied.

Give each criterion a unique :id and a :description. Use :gates to list the checks that count as evidence for that criterion. The model cannot weaken the criteria or accept results on your behalf. Only the primary agent can use the mission.status, mission.verify, mission.stop, and mission.invalidate tools.

Mission budgets cover parallel work as well as the primary agent:

  • Turns. Each provider call uses a turn, including calls from children, compaction, recursive inference, and independent review. Admissions and settlements are serialized within a mission. Provider calls can run in parallel.
  • Tokens. Each admitted call reserves tokens from the unspent and unreserved budget. The default allocation divides them among the remaining turns. An explicit provider output cap replaces that allocation. On settlement, Autolith releases the reservation and charges reported input and output usage. Provider normalization excludes known prompt-cache reads. Measured usage can exhaust the budget.
  • Wall time. The deadline includes gates, tools, pauses, and time away.

If a child call reports no usage, Autolith charges the full finite reservation once if it can identify the exact child and reservation. It records the failure and the unknown usage. The charge is already included in :tokens-used. Use :reservation-charged-tokens for the total and :reservation-charges-by-child for the breakdown. The child result lists :unknown-usage, :reservation-charged-tokens, and :reservation-charge-requests. The :usage field contains only measured usage.

A reservation charge is an accounting rule, not a provider billing or output limit. Input and repeated generations can cost more. At the current library pin, Codex does not enforce an output ceiling on the wire. A successful retry charges the final reported usage without reconciling unreported attempts.

The default :block policy blocks new inference if missing usage cannot be settled, including missing primary usage or uncertain child ownership. Already reserved requests and continuations that spend no tokens can finish. Restoring the session cannot recover per-request bounds from aggregate reservations or reclassify unresolved usage.

To proceed despite missing usage, select :unknown-usage-policy :record when you start the mission:

Common Lisp 
(mission :start
 '(:objective "Run the periodic checks"
   :turn-limit 10000 :token-limit 10000000 :wall-seconds 86400
   :unknown-usage-policy :record
   :criteria ((:id "checks" :description "The user accepts the checks"))))

Under :record, Autolith records failed or interrupted calls whose usage cannot be settled and can continue without that measurement. It still charges exact child reservations if possible. Turn and wall-clock limits apply, and independent reviewers still need reported usage. To change the policy for existing work, start a new mission with the criteria and budgets and add the policy key. Large integer limits are finite.

  • Pause with (goal :pause) and resume with (mission :resume). These commands do not reset the budget.
  • Cancel with (mission :cancel "REASON").
  • Inspect a blocked mission with (mission :status). Resolve the blocker before resuming. The terminal states are verified, exhausted, cancelled, and failed.

Autolith saves gate attempts, fingerprints, and evidence with the conversation so you can inspect them after a restore or compaction.

Gates run in order and stop at the first failure:

  • Command gates use the normal shell authorization and sandbox boundary.
  • Artifact gates require :path. Set :sha256 to check an expected hash.
  • Lisp gates require a :predicate string. The assertion runs in the existing isolated Lisp worker.

Every gate supports :timeout-seconds and a separate :attempt-limit. The defaults are 60 seconds and three executions. Each gate keeps bounded evidence.

For deterministic gates, declare all relevant file paths in :inputs and set :deterministic-p t. File contents and missing-file states form the fingerprint; directory paths are rejected. Unchanged passing gates supply current proof, and unchanged failed gates are withheld while the model works on their relevant inputs. For remote state, omit deterministic policy or invalidate a particular gate explicitly:

Common Lisp 
(mission :invalidate "build" "The remote build configuration changed")

Invalidation permits another execution without replenishing its attempt budget. Before acceptance, every gate fingerprint is checked again under the workspace mutation lock. Changes from a later gate invalidate earlier passing evidence. Collect terminal results and outstanding inference usage before verifying.

Independent review checkpoints

Attach a reviewer to an active mission with mission-review.configure, or evaluate:

Common Lisp 
(application-mission-review-configure
 *active-application*
 '(:id "release-review" :phase :final-acceptance
   :inputs ("src/main.lisp" "tests/main-tests.lisp")
   :context "Review the changed behavior and test coverage. Report concrete findings."
   :turn-limit 4 :token-limit 16000 :run-limit 3))

Declare all relevant files. The reviewer receives an independent snapshot and background and returns findings in the required form. The reviewer has no tools or spawning permission. Reviewer calls and tokens count against both the cumulative reviewer allowances and the mission allowances, including reviews of changed snapshots. :run-limit bounds the number of distinct snapshots reviewed.

Use mission-review.trigger with id to review a checkpoint and mission-review.inspect to read its durable findings, decisions and usage. Unchanged snapshots reuse completed, failed or interrupted runs. Resolve or reject each finding through mission-review.decide with id, finding, decision (resolve or reject) and an evidence-bearing reason. Only the primary agent or local user may configure, trigger and adjudicate reviews.

Final verification runs configured final-acceptance checkpoints. Pending findings and failed or interrupted reviews block acceptance. For before-integration and after-edit-set checkpoints, trigger the named review explicitly at the chosen boundary. Reviewer findings are advisory; mission gates and user acceptance supply harness evidence.

Scheduled mission continuations

Attach explicit wakeups to the current mission with mission-schedule.add. Supply an immutable id, continuation content, and one time policy. at is an absolute Common Lisp universal time. interval is a positive number of seconds. event names an external event instead. For example:

Common Lisp 
(application-mission-schedule-add
 *active-application* :id "build-followup"
 :content "Check the pending build and continue the mission."
 :at (+ (get-universal-time) 300) :missed-policy :latest)

For recurring wakeups, choose missed-policy latest (the default), all, or skip. These select the newest missed occurrence, every missed occurrence, or only an occurrence due at exactly the current time. Use mission-schedule.event with an event name and stable external event id; repeated delivery of that ID is deduplicated. The local daemon listener hosts time wakeups. Due work is persisted in the ordinary primary command queue as (mission-wakeup ticket), where ticket is structured data. The command runs as a mission continuation under the existing turn, token, and wall-clock budgets.

While a hosted time wakeup of the current mission version is due later or already admitted, automatic goal continuations stop and the mission stays active. The model is not prompted again between occurrences. Within an occurrence, work continues through the turn's own tool calls and through job completions. Event schedules, cancelled schedules, and a finished one-shot wakeup leave ordinary continuations in place. A user message or (goal :resume) still runs its own turn.

Only the primary agent may use the mission-schedule tools. Each wakeup keeps its exact mission identity and version. Both are checked at admission and execution.

While the mission is paused or blocked, the missed policy skips due occurrences without running them. The interval advances. After a resume, the next due occurrence arrives without recreating the schedule. Skipped occurrences are not replayed, including one-shot wakeups and deduplicated events. With the default :block policy, unknown usage prevents mission resume. :record does not prevent an independent pause or blocker from resuming.

The schedule is cancelled when the mission is replaced, its version changes, or it reaches a terminal state (verified, exhausted, cancelled, failed or legacy complete). Skips and automatic cancellations produce persisted user notices. Use mission-schedule.inspect to read schedules, occurrence IDs, claim tokens and outcomes: skipped occurrences have state cancelled with result (:skipped <mission-status>); obsolete mission work has result :stale-mission and a cancelled schedule. Use mission-schedule.cancel with the schedule id to cancel future and pending work.

Interrupted admissions and executions restore as uncertain outcomes. Inspect the external effects before calling mission-schedule.resolve with the readable occurrence ID, current token and action completed, failed or retry. Retry is an explicit decision and is refused while the occurrence is executing. Cancellation retains claim and duplicate history.
